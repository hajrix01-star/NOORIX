# خطة الإصلاح الشامل في NOORIX

هذه الخطة هي مرجع تنفيذي وأودتر للتغييرات المطلوبة قبل الاعتماد النهائي. الهدف ليس ترقيع مواضع منفصلة، بل تثبيت قاعدة منصة واضحة: كل رقم رسمي في النظام له مصدر واحد، والواجهة تعرض أو تجمع مدخلات فقط، ولا تصنع حقيقة مالية بديلة.

## القاعدة الحاكمة

- قاعدة البيانات هي مصدر الحقيقة للبيانات المحفوظة.
- السيرفر هو مصدر الحساب والتنفيذ الرسمي لأي أثر مالي أو نظامي.
- الواجهة لا تعتمد كمرجع نهائي؛ دورها إدخال، عرض، تنسيق، ومعاينة فقط.
- يمنع fallback محلي يعوض فشل المصدر المركزي في الأرقام المالية أو HR.
- أي عملية مالية مؤثرة يجب أن تكون قابلة للإعادة بأمان قدر الإمكان، مع قيد قاعدة بيانات يمنع التكرار عند الحاجة.
- يسمح برصيد خزينة سالب فقط إذا كان ناتجا من ledger مركزي صحيح، وهذا استثناء مقصود وليس سماحا بكسر القيد المزدوج أو حساب محلي بديل.

## نطاق الإصلاح

| المجال | المطلوب | الحالة |
|---|---|---|
| قاعدة المصدر الواحد | توثيق قاعدة عامة تشمل النظام كامل بجميع أقسامه | تم |
| HR | ربط رواتب الموظف، المخالصة، نهاية الخدمة، السلف، ومسيرات الرواتب بالمصادر المركزية | تم سابقا ضمن خطة HR، وتم تعزيز القاعدة العامة |
| الفواتير والضريبة | منع اعتماد صافي/ضريبة قادمة من الواجهة في فواتير المصروف/المشتريات | تم |
| تحديث الفاتورة | إعادة احتساب الصافي والضريبة في السيرفر عند تعديل الإجمالي/الضريبة | تم |
| صلاحية الضريبة | فصل تعديل إعدادات VAT عن صلاحية تعديل بيانات الشركة العامة | تم |
| إصدار مسير الرواتب | جعل إصدار فاتورة الراتب قابلا للإعادة بأمان ولا يكرر فاتورة لنفس المسير | تم |
| حماية قاعدة البيانات | إضافة قيد فريد يمنع تكرار فاتورة راتب نشطة لنفس مسير الرواتب | تم |
| OCR VAT | ربط نسبة الضريبة في OCR بالمحرك المركزي بدل رقم ثابت محلي | تم |
| CI | إضافة فحص الملفات الكبيرة إلى مسار CI حتى لا تتراكم ملفات يصعب صيانتها | تم |
| اختبارات الحساب | إضافة/تحديث اختبارات لمسارات الفاتورة، مسير الرواتب، و OCR | تم |
| اختبارات البنية | تشغيل typecheck/build/test على الواجهة والسيرفر | تم |
| تدقيق الاعتماديات | فحص npm audit وتسجيل المخاطر المتبقية | تم، ويتطلب مسار ترقية مستقل |

## شروط القبول

- لا تقبل الواجهة كحقيقة نهائية لأي رقم مالي أو HR رسمي.
- لا يوجد مسار إصدار مالي يعتمد على صافي/ضريبة مرسلة من العميل دون إعادة احتساب أو تحقق مركزي.
- لا يمكن تكرار فاتورة راتب نشطة لنفس مسير الرواتب بسبب retry أو ضغط متكرر.
- صلاحية تعديل VAT مستقلة عن تعديل بيانات الشركة العامة.
- كل إصلاح له اختبار أو فحص مناسب حسب مستوى الخطر.
- أي مشكلة اعتماديات تتطلب ترقية major أو استبدال مكتبة تسجل بوضوح ولا تخلط مع إصلاحات الحسابات الحساسة.

## ما لا يجب فعله لاحقا

- لا تعاد إضافة fallback محلي للأرقام الرسمية.
- لا تنسخ معادلات مالية في مكونات React إلا كمعاينة صريحة يعاد تحققها في السيرفر.
- لا تحفظ نتائج محسوبة من الواجهة كحقيقة نهائية.
- لا توسع صلاحية إدارية عامة لتشمل VAT بدون قصد واضح.
- لا تنفذ ترقيات major للاعتماديات داخل دفعة إصلاح حسابي حرجة دون خطة اختبار منفصلة.

## البنود المتبقية المقصودة كمسار منفصل

| البند | السبب | المسار المقترح |
|---|---|---|
| ثغرات npm audit في الجذر | بعضها يحتاج ترقية Vite/React Router/DOMPurify، و `xlsx` لا يملك إصلاح مباشر | PR مستقل لترقية أو استبدال مع اختبارات واجهة |
| ثغرات npm audit في backend | إصلاحها المقترح يتطلب ترقيات major في Nest/Express ومكتبات مرتبطة | PR مستقل لترقية backend framework مع smoke tests و migration rehearsal |
| تفكيك الملفات الكبيرة | الفحص أصبح موجودا في CI، لكن التفكيك يحتاج خطة refactor تدريجية | تنفيذ على دفعات صغيرة بعد استقرار الحسابات |

## حالة الإغلاق

تغلق هذه الدفعة عند نجاح:

- اختبارات backend المركزة.
- اختبارات backend الكاملة.
- اختبارات الواجهة.
- typecheck.
- build للواجهة والسيرفر.
- فحص `git diff --check`.
- تسجيل مخاطر `npm audit` المتبقية بدون إخفائها.
