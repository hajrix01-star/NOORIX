# طلبات 2 — نواة V3 وعقد التحويل والترحيل

## الهدف وحدود الاستقلال

`طلبات 2` هو نظام مستقل، وليس شاشة جديدة فوق نظام الطلبات القديم. حدوده التقنية هي:

- الواجهة: `src/modules/OrdersV3`.
- الخادم: `backend/src/orders-v3`.
- واجهة HTTP: `/api/v1/orders-v3`.
- قاعدة البيانات: الجداول التي تبدأ بـ `orders_v3_`.
- الصلاحيات: `orders_v3.*` فقط.

يُمنع على V3 استيراد خدمات أو نماذج أو نقاط API من `Orders` القديم. المسموح أثناء الترحيل هو قارئ ترحيل أحادي الاتجاه يسجل كل ربط في `orders_v3_migration_map`، ولا يصبح جزءاً من تشغيل V3 اليومي.

## ما هي النواة V3؟

النواة هي المصدر المركزي الوحيد للقرارات الرقمية والحركية، وتتكون من ستة أجزاء:

1. **نواة الكتالوج:** الصنف، الوحدة الأساسية، الأقسام، التصنيفات، المواقع، وحالة التفعيل.
2. **نواة التحويل:** تحل أي كمية من وحدة إدخال إلى الوحدة الأساسية للصنف عبر نسخة تحويل منشورة وغير قابلة للتعديل.
3. **نواة الحساب:** تحسب كمية الأساس، سعر وحدة الأساس، إجمالي السطر، والتكلفة، باستخدام أرقام عشرية دقيقة فقط.
4. **نواة سير العمل:** تنشئ مستند شراء أو تسجيل داخلي، تمنع التكرار بمفتاح idempotency، وتنفذ العكس بمستند/قيود مقابلة.
5. **نواة المخزون والتكلفة:** دفتر حركات append-only؛ لا تعدل الحركة بعد تسجيلها. الرصيد والتكلفة يعاد اشتقاقهما من الدفتر.
6. **نواة التقارير:** تعرض projections من نفس المستندات والدفتر، فلا توجد معادلات مكررة داخل الشاشة أو التقرير.

الخادم هو صاحب الرقم الرسمي. الواجهة تجمع المدخلات وتعرض الناتج، لكنها لا تعتمد سعراً أو تحويلاً أو رصيداً نهائياً من عندها.

## قاعدة التحويل المركزية

لكل صنف وحدة أساس واحدة. تُحوّل الكمية وفق المسار المنشور:

`baseQuantity = enteredQuantity × product(all edge factors in the resolved path)`

ثم يحسب سطر التكلفة:

`baseUnitPrice = enteredUnitPrice ÷ priceUnitFactor`

`lineTotal = baseQuantity × baseUnitPrice`

قواعد السلامة:

- الحسابات تستخدم `Decimal` ولا تستخدم أرقام JavaScript العائمة للحساب الرسمي.
- التحويل العام داخل البعد نفسه يمكن أن يعتمد العامل القياسي للوحدة.
- تحويلات تغليف الصنف، مثل كرتون ← حبة، تحفظ كحواف تخص الصنف.
- تحويل بين بعدين مختلفين، مثل كجم ← لتر، مرفوض افتراضياً؛ لا يسمح به إلا كجسر صريح للصنف مع `allowDimensionBridge`.
- يمنع نشر دورة تحويل، أو مسارين يعطيان عاملين مختلفين، أو عامل صفر/سالب.
- النسخة المنشورة immutable. التغيير ينشئ نسخة جديدة، والمستند يحتفظ بنسخة التحويل التي استخدمها.
- الوصفة نسخة منشورة مستقلة؛ الاستهلاك يحوّل كل مكوّن إلى وحدة أساسه ثم يضيف الهدر المحدد.

## قاعدة التكلفة والمخزون

- الشراء يضيف كمية أساس وتكلفة فعلية إلى الدفتر.
- متوسط التكلفة المرجح بعد الاستلام:

  `(oldQuantity × oldAverage + receivedQuantity × receivedUnitCost) ÷ newQuantity`

- الصرف/التسجيل يستهلك بالتكلفة التاريخية المركزية وقت الترحيل.
- الجرد لا يكتب فوق الرصيد؛ يسجل حركة فرق موجبة أو سالبة.
- العكس يضيف قيوداً معاكسة مرتبطة بالمصدر، ولا يحذف القيد الأصلي.
- كل عملية كتابة تحمل `companyId`، مفتاح idempotency، وهوية المنفذ ووقت التنفيذ.

## خريطة البيانات من القديم إلى V3

| القديم | V3 | قاعدة النقل |
|---|---|---|
| `OrderCatalogUnit` | `OrdersV3Unit` | توحيد الكود والبعد والعامل القياسي |
| `OrderCategory` | `OrdersV3Category` | نقل الاسم والحالة مع سجل mapping |
| `OrderSection` | `OrdersV3Section` | نقل الكود والاسم والحالة |
| `OrderProduct` | `OrdersV3Item` | تعيين وحدة أساس صريحة قبل القبول |
| تحويلات الصنف | `OrdersV3ConversionVersion/Edge` | تنظيف الرسم ثم نشر نسخة واحدة موثقة |
| وصفات الصنف | `OrdersV3RecipeVersion/Line` | تحويل المكونات إلى معرفات V3 ونشر نسخة |
| `Order/OrderItem` | `OrdersV3Document/Line` | مستند نوع `purchase` مع إعادة حساب ومطابقة الإجمالي |
| `StaffOrder/StaffOrderItem` | `OrdersV3Document/Line` | مستند نوع `registration` مع حفظ المصدر |
| حركات المخزون القديمة | رصيد افتتاحي/دفتر V3 | لا تنسخ الحركة غير الموثوقة آلياً؛ تطابق snapshot ثم تقيد افتتاحياً |

كل سجل منقول يجب أن يملك سطراً في `orders_v3_migration_map` يحتوي نوع وID المصدر، نوع وID الهدف، checksum، والحالة. بذلك يمكن إعادة تشغيل الدفعة بأمان ومعرفة أي سجل لم ينتقل.

## مراحل القطع وحذف النظام القديم

1. نشر schema وV3 دون تحويل المسارات الحالية.
2. ترحيل الكتالوج والتحويلات والوصفات في وضع dry-run، ثم حل الأخطاء.
3. ترحيل المستندات التاريخية على دفعات idempotent، مع مقارنة العدد والإجماليات لكل شركة/يوم.
4. اختيار لحظة قطع، تجميد الكتابة القديمة، وأخذ snapshot للمخزون والتكلفة.
5. إنشاء الأرصدة الافتتاحية في V3 ومطابقة الكمية والقيمة على مستوى الصنف والموقع.
6. تحويل القائمة والصلاحيات إلى V3 ومراقبة عدم وصول أي طلب إلى API القديم.
7. أخذ نسخة احتياطية قابلة للاستعادة ثم حذف كود ومسارات وجداول القديم في migration منفصلة.

لا يسمح ببوابة الحذف إلا إذا تحقق الآتي كله:

- لا يوجد سجل نشط بلا mapping موثّق.
- أعداد المستندات وإجمالياتها متطابقة، والفروق موثقة ومقبولة بصفر فرق غير مفسر.
- كمية وقيمة المخزون متطابقتان لكل صنف وموقع.
- كل صلاحيات ومسارات وعمليات الخلفية تحولت إلى V3.
- سجل المراقبة يؤكد عدم استخدام API القديم خلال فترة الثبات المتفق عليها.
- توجد نسخة احتياطية مجربة الاستعادة وخطة rollback.

حذف النظام القديم ليس جزءاً من migration إنشاء V3؛ ينفذ فقط في migration قطع مستقلة بعد اجتياز هذه البوابات.

يمكن تشغيل مدقق القطع الآمن للقراءة فقط بعد نشر migration وترحيل الدفعات:

`cd backend && npm run audit:orders-v3-cutover -- --company-id <company-id>`

يعيد المدقق حالة `ready` وتغطية mapping وفروق إجمالي الشراء ووجود snapshot مخزون موثّق. نجاحه لا يتجاوز شرط اختبار استعادة النسخة الاحتياطية وشرط انعدام حركة API القديم.
