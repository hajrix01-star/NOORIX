# طلبات V4 — عقد مركزية الوحدات والمخزون

## القرار المعماري

طلبات V4 يملك نواة تحويل وحساب مستقلة. لا يجوز لأي شاشة أو خدمة أعمال تنفيذ معادلة تحويل أو كتابة قيد مخزون بنفسها.

المسار الإلزامي هو:

`الخدمة التشغيلية → نواة التحويل/الحساب → بوابة ترحيل المخزون → سجل المخزون غير القابل للتعديل`

## مصادر الحقيقة

| المسؤولية | مصدر الحقيقة الوحيد |
|---|---|
| إيجاد مسار التحويل ومعامله | `orders-v4-conversion.kernel.ts` |
| تجهيز سياق الوحدات والحواف لكل الخدمات | `orders-v4-conversion.context.ts` |
| كمية وسعر سطر الطلب | `orders-v4-calculation.kernel.ts` |
| تكلفة الرسبي ومتوسط آخر 5 أسعار | `orders-v4-calculation.kernel.ts` |
| الاستلام والصرف والجرد والعكس وتغيير وحدة المخزون | `orders-v4-ledger-posting.service.ts` |
| عرض الرصيد | آخر قيد لكل صنف وموقع في `orders_v4_inventory_ledger` |

## قواعد الوحدات

1. كل صنف يملك وحدة مخزون حالية واحدة.
2. الوحدات الأخرى ترتبط بها بمسارات تحويل منشورة وذات نسخ تاريخية.
3. التحويل متعدد المستويات مدعوم؛ مثال: كرتون ← علبة ← حبة.
4. المستند يحفظ وحدة الإدخال، وحدة السعر، وحدة الأساس وقت العملية، ونسخة التحويل.
5. سعر الشراء التاريخي يحفظ وحدة السعر ووحدة المخزون التي حُسب عليها.
6. كل قيد مخزون يحفظ وحدة المخزون الخاصة بالقيد، ولا يعتمد على الوحدة الحالية في بطاقة الصنف.
7. لا يمكن تعطيل وحدة مرتبطة بصنف أو تحويل أو رسبي أو مستند أو سعر أو مخزون تاريخي.
8. إعادة نشر نفس النسخة الحالية عملية خاملة، أما الرجوع إلى تعريف متوقف سابقًا فينشئ نسخة منشورة جديدة قابلة للتدقيق.

## تغيير وحدة المخزون

تغيير وحدة المخزون عملية محاسبية وليست إعادة تسمية:

1. يتحقق النظام من وجود مسار تحويل من الوحدة السابقة إلى الجديدة.
2. ينشر نسخة تحويل جديدة مرتبطة بالوحدة الجديدة.
3. ينشئ قيد `unit_rebase` لكل موقع له رصيد.
4. يحول الكمية ومتوسط التكلفة، مع تثبيت إجمالي قيمة المخزون دون تغيير.
5. يمنع حذف أي وحدة مستخدمة تاريخيًا في مستند أو سعر أو رسبي أو قيد مخزون.

مثال: رصيد 2 كرتون بقيمة 576، وكل كرتون 288 حبة، يصبح 576 حبة بقيمة 576 ومتوسط تكلفة 1 للحبة.

## قواعد المخزون

- الاستلام يزيد الكمية والقيمة ويعيد حساب المتوسط المرجح.
- التسجيل الداخلي يصرف مكونات الرسبي بالتكلفة التاريخية للرصيد.
- الجرد ينشئ فرقًا فقط ولا يعدل القيد السابق.
- العكس ينشئ قيدًا معاكسًا، ويحول كمية القيد التاريخي إلى وحدة المخزون الحالية إن تغيرت.
- سجل المخزون append-only ومحمي من التعديل والحذف على مستوى قاعدة البيانات.
- قفل كل `صنف + موقع` إلزامي قبل الترحيل لمنع تضارب العمليات المتزامنة.

## قاعدة تكلفة الرسبي

لكل مكوّن:

1. تؤخذ آخر خمسة أسعار من طلبات شراء مستلمة فقط.
2. يحول كل سعر تاريخي من وحدة المخزون المسجلة معه إلى وحدة المخزون الحالية.
3. يحسب المتوسط البسيط للعينات المتاحة (حتى خمس عينات).
4. تحول كمية المكوّن في الرسبي إلى وحدة مخزونه.
5. التكلفة = كمية الصرف بوحدة المخزون × متوسط السعر الموحّد.

## حواجز منع التشتت

- اختبار حدود آلي يفشل إذا كتبت أي خدمة في سجل المخزون خارج بوابة الترحيل المركزية.
- اختبار حدود آلي يفشل عند ظهور حسابات رصيد مباشرة خارج النواة.
- اختبار حدود آلي يمنع استدعاء محلل التحويل خارج سياق التحويل المركزي.
- حساب فرق الجرد وإنشاء سطره وقيده تتم كلها داخل بوابة الترحيل.
- اختبارات النواة تغطي التحويل متعدد المستويات، السعر التاريخي، الرسبي، إعادة أساس الوحدة، والعكس بعد تغيير الوحدة.

## معيار القبول

تعد المركزية مكتملة فقط عندما:

- لا توجد كتابة مباشرة إلى `ordersV4InventoryLedgerEntry.create` خارج `orders-v4-ledger-posting.service.ts`.
- لا تعتمد شاشة أو تقرير على وحدة الصنف الحالية لشرح قيد أو سطر تاريخي.
- تغيير وحدة المخزون لا يغير إجمالي القيمة ولا يعيد تسمية الكميات القديمة بصمت.
- الاستلام والصرف والجرد والعكس وإعادة الأساس تمر عبر نفس البوابة ونفس نواة الحساب.
